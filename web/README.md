# CP7 local synthetic web increments

React + TypeScript + Vite SPA authorized by PD-0042. CP7-A provides ephemeral
guests; CP7-B adds local accounts and PostgreSQL-backed fictional sandboxes.
CP7-C adds audited CSV import/export; CP7-D connects revision-pinned performance
and risk questions. See the [current D verification and acceptance record](../reviews/CP7_D_PM_ACCEPTANCE.md);
these increments do not authorize a release. Financial facts come from the Python
CP3/CP4/CP5/CP6 engines through the versioned API; this folder contains no portfolio
sum, weight, FX conversion, severity or financial-threshold computation.

## Local development

Node 26+ is required by this locked and verified toolchain. Dependency installation
is the bounded allowance already approved in PD-0042; additional production
dependencies need their own approval. `package-lock.json` is generated by npm,
not hand-written. Use `npm ci --ignore-scripts` to reproduce the reviewed install.

Start the explicitly enabled local synthetic API from the repository root:

```sh
PYTHONPATH=src uv run --no-cache --no-sync --frozen --offline uvicorn web_api.dev:app --host 127.0.0.1 --port 8000
```

Then, in `web/`:

```sh
npm run dev
```

The Vite development server is `http://127.0.0.1:5173`; `/api` is proxied to the
local API at port 8000. Both processes stay on loopback. No external data,
external identity provider or deployment is used. See
`implementation/CP7_TECH_PLAN.md` for guest enablement and the additive
`implementation/CP7_B_TECH_PLAN.md` for account/PostgreSQL configuration and the
origin boundary. Account storage must be configured explicitly; the old
memory-only guest launch is not evidence of durable saving.

The form loads supported listings and example quantities from `/capabilities`.
It requires a synthetic acknowledgement; only fictional SYN-A/SYN-B opening
positions and USD cash are supported. CNY is visibly disabled because the route
has no supporting FX path. Interface language does not change reporting currency.

Guest capabilities and portfolio state stay in memory. Capabilities are never
placed in a URL, local storage or session storage. A 401 invalidates the token;
the next explicit form retry can create a fresh guest session. “New guest
portfolio” clears the previous capability. Nothing is saved to a user account.

## Local accounts and saved synthetic sandboxes

Use **Sign in → Create local account** to create an isolated local account, or
sign in with an existing local account. Credentials are entered only into the
local form and sent to the same-origin API. Use unique disposable test credentials
for this local review. The account form does not install or connect an external
authentication service. Normal account sessions use HttpOnly SameSite=Strict
cookies and server-issued CSRF tokens. Browser code keeps the CSRF token only in
memory; it never stores passwords, session cookies, guest capabilities or user
portfolio data in local/session storage or URLs. Production deployment still
requires HTTPS and the reviewed server configuration; loopback testing is not a
deployment authorization.

**New saved synthetic portfolio** creates a new explicitly acknowledged fictional
sandbox belonging to the signed-in user. Its schema discriminator is
`LOCAL_SYNTHETIC_ACCOUNT`, `synthetic: true`, `persisted: true`. It is stored in
PostgreSQL and can be selected from **Your saved synthetic portfolios** after a
browser/application reload. Opening it obtains the stored inputs and exact engine
results from the backend. Evidence and reproduction use the authenticated route.
Guest portfolios are never automatically copied, promoted to real holdings, or
saved on sign-in. **New guest portfolio** remains an explicitly separate ephemeral
flow, including while signed in.

Identity changes, logout and protected-route session/CSRF refusals clear the
displayed private snapshot, saved list and Proof Packet. AbortController plus a
generation check discards pending old responses, including late JSON decoding.
An identity-only BroadcastChannel message clears other same-origin tabs; returning
to a visible authenticated tab rechecks the server session before restoring any
saved-list access. This channel contains no credentials, user identity or portfolio
data. Foreign and nonexistent resource IDs receive the same canonical refusal;
the frontend never guesses a missing owner's identity.

## Implemented and deferred

Implemented: a guest/manual synthetic portfolio, local registration/login/logout,
owned PostgreSQL saved-sandbox create/list/open/reload, server-valued current snapshot,
capital exposures, deterministic CP6 observations, exact strings and canonical
identities, source-scoped evidence, actual result reproduction, EN/zh-CN,
Quick/Simple/Professional, a responsive four-surface shell and a native modal
with Escape/focus-return behavior. The saved Portfolio surface also exposes:

- Canonical native balances and complete ledger facts with immutable audit links;
  append, reversal, atomic correction batches, account containers, actual server
  validation/rollback preview and explicit confirmation. Event-specific fields
  come from the issued domain rules. Internal transfers require both legs.
- Explicit immutable revision history. Opening an old revision pins its snapshot,
  Proof Packet and reproduction URL to that revision. Historical views are read
  only. The initial opening inputs remain labelled separately from current native
  balances; no browser financial arithmetic derives a current holding or NAV.
- Optional blank personal-limit fields, exact signed decimal/fraction transport,
  explicit scope/semantic identity, user evidence and effective dates. A save
  confirms the full set; removing all rows records no limits. Personal limits do
  not alter FULL_NAV/GLOBAL_PRODUCT or create a risk profile.
- Distinct never-stated, explicitly-none and admitted benchmark selection states.
  The committed catalog is empty, so selecting is visibly unavailable; no SPY
  default or market data is invented. Recording no benchmark remains possible.

Previews are uncommitted and carry `persisted: false`; only the explicit preview
reader accepts them. They never enter the saved snapshot or Proof Packet reader.
Confirmation uses the same operation ID and expected revision. Manual unchanged
retries preserve that ID; stale revisions and changed-content reuse are refused.
Identity/session changes clear all these forms, revisions and pending responses.
The source fixture still covers only 2026-01-02: later ledger facts can reconstruct
native balances while valuation honestly suppresses unsupported date/FX inputs.

Before CSV and D, the additional workspace Playwright flow brought the suite to
six tests and five disposable registrations, including prior account flows.
It exercises rollback, edited-preview invalidation, append/correction, immutable
old proof reproduction, explicit limits/equality/no-benchmark states, stale-head
refusal, reload and Chinese narrow rendering. Coordinate actual DB/browser runs
with the PM so suites remain serialized and the durable registration limit is
respected. A test definition alone is not a passing run.

The Portfolio CSV surface adds two explicit fictional import modes. Holdings
create one named new account at the supported 2026-01-02 opening date; transaction
facts append to explicitly owned existing accounts. Choose the delimiter, date,
decimal and grouping rules and map zero-based column indexes. No header matching,
security/account guessing, missing-currency/date/quantity fill or average-cost
calculation occurs in the browser. Raw UTF-8 bytes, BOM, quoted newlines, original
cells, correction reasons and explicit nondata/out-of-scope classifications stay
auditable in the server report.

Any unresolved intended economic record or whole-batch refusal blocks every
financial write. The only confirmation then available saves a zero-import report;
it creates no account or revision. A user-confirmed nondata/out-of-scope row needs
a reason. Repreview after correcting facts. Complete valid imports atomically save
the canonical ledger revision, source keys and report. Stable source namespace,
account/snapshot/row identities prevent a new operation UUID from duplicating the
same source; identical independent trades with distinct source keys stay distinct.

The raw file limit is 16 KiB. The entire actual UTF-8 JSON request, including
base64, mappings, corrections and confirmation receipt, must remain within 32 KiB.
The expanded canonical audit report is separately limited to 2,000,000 UTF-8 bytes;
an oversized report refuses the whole proposal before persistence. Simplify redundant
mapping/correction text while preserving all intended facts; truncation or splitting
the intended batch is not a capacity workaround.
Other resource bounds are 128 logical records, 32 columns, 2,048 UTF-8 bytes per
cell, 32 new events and 1,000 durable reports per portfolio. Maxima cannot always
be combined. Exact operation retries do not consume a new report. The indexed
mapping is cleared when parsing rules change; every proposal edit invalidates the
owner/operation/head/source-bound server receipt and explicit confirmation.
Uncertain network results preserve the same operation for an unchanged retry.

Owned reports use visible pagination, refresh and typed cursor-expiry recovery.
CSV and lossless JSON exports are authenticated, no-store and explicitly scoped to
the selected report or immutable portfolio revision. CSV apostrophe protection is
disclosed; spreadsheet compatibility is not universally guaranteed. Authoritative
JSON retains original text and audit data. Exact nondecimal replay quantities are
not rounded or promised to fit the decimal-only CSV import boundary.

The CSV browser scenario uses one disposable registration; the C suite had seven
tests and six registrations. It covers mixed valid/invalid
whole-batch quarantine, correction provenance, source no-op, distinct identical
trades, explicit footer classification, downloads, old proof, bilingual narrow
layout and clearing an active file/receipt on logout. Actual reruns require the
PM's serialized database/browser slot; the checked-in scenario alone is not
execution evidence.

## F3 guarded fictional profile

The separate, explicitly provisioned F3 profile reuses this app and local account
login. Its reviewed API is `127.0.0.1:8003`; the additive `vite.f3.config.ts` serves
`127.0.0.1:5174` and proxies only that new API, with `.env` loading disabled.
The legacy server/configuration and guest flow remain separate and unchanged.
Root owns the isolated PostgreSQL Unix55433 setup and app configuration; the UI
does not provision a database, issue permissions or read connection credentials.

After the reviewed runtime is explicitly started, the frontend command is the
already installed Node/Vite CLI with `--config vite.f3.config.ts --host 127.0.0.1`.
Use `node node_modules/typescript/bin/tsc --noEmit` for typecheck, the root-provided
temporary Vitest configuration with `envDir:false` for tests, and
`node node_modules/vite/bin/vite.js build --config vite.f3.config.ts` for its build.
No npm install, npx download, browser install or ambient `.env` is needed. These
commands document the candidate; actual run results belong to F3 evidence.

Sign in with a disposable local account, create an explicitly fictional saved
portfolio, and check the **Opening facts date** separately from the fixed source
valuation date. January1 opening permits ordinary January2 activity; same-day
ordinary events following a January2 opening still refuse. The browser never
adjusts a source date or supplies a real price to make a calculation succeed.

For a normal commit, the client hashes exact server-stored `response_json` before
using its Snapshot/Workspace/Csv reader. It never promotes a staged preview to
saved state. An uncertain response retains the same operation and unchanged
request in memory. **Check this operation** queries the server; **Retry unchanged
operation** deliberately resends those original bytes. Neither runs automatically,
and absence is not proof of rollback. Lost creation responses have a separate
authenticated operation lookup; the client does not derive a portfolio UUID.
Reloading or an identity reset loses in-memory pending inputs; owned committed
operations are rediscovered through the authenticated saved list and current head.

The Portfolio archive panel separately reads, downloads and reproduces the exact
CP5 artifact. Raw UTF-8 hashes and original root/operation/revision/native bindings
are checked before display. Current admission generation and original issuance
generation are labelled separately. A normal archive read performs no financial
recomputation; reproduction is explicit and needs a separate current permission.
Only a verified `REPRODUCED` with the expected issued SHA is presented as success.
Historical performance/risk requests, old packets, real data and guest creation
are visibly unavailable in this profile; no legacy financial fallback is used.

The new browser scenario uses two disposable identities, the existing installed
Chrome in a temporary profile, and only the new owned loopback origins. Shared
browser-test registrations stay within the root's six-registration budget; no
limiter reset is used. Credentials/cookies/CSRF, private drafts and CSV contents
are never placed in web storage or retained browser traces. Complete personal
fictional-trial readiness and user acceptance are recorded separately from this
technical implementation. Real-data UAT, D3, HG4, installs, commits/deployment and
the stopped night automation retain their existing conditions.

## F1 R7 real mode (TEST install data only until R8)

A separate profile: its own page (`real.html`), Vite config (`vite.real.config.ts`, port 5175, `/api` proxied to the launcher on 8004), launcher
(`src/web_api/real_launcher.py`) and strings (`real-mode-i18n.ts`). It talks only to `/api/v1/auth/*` and the four scoped routes under
`/api/real/v1/roots`; every other `/api/*` path is a closed refusal (503 `REAL_MODE_ROUTE_CLOSED`). It is not the fictional account app and shares no list
type with it. Over a `SYNTHETIC_TEST` root the screen shows the invented-data mark and no real-source sentence; the claim-limit text (design 7.4) is
rendered only for a stored `REAL_SOURCE` origin, in English and Chinese at three depths, from the slots of the stored lineage. Below the claim limits the
detail shows a read-only list of key figures (PD-0079: a fixed list of metric ids, each with its stored value, state and reason as stored; no number on
`INSUFFICIENT_DATA`; the client computes nothing), then the issued document collapsed under a label that says what it is.

Run recipe (four terminals, from the project root; the PostgreSQL development cluster must be running; the admin role is a superuser of that cluster):

1. `FINWEB_PG_INTEGRATION=1 FINWEB_PG_SOCKET=/tmp/.s.PGSQL.5432 FINWEB_PG_DATABASE=finweb_dev FINWEB_PG_USER=finweb_dev FINWEB_PG_ADMIN_USER=<admin> uv run --no-cache --no-sync --frozen --offline python tests/product/real_dev_env.py --contexts-file "$TMPDIR/real-mode-contexts.json"` (stays in the foreground and prints one JSON line, flushed at once). **It exits, and drops its database, as soon as stdin reaches end of input**, so when it is started without a terminal (a background job, a pipe) keep stdin open, for example `tail -f /dev/null | uv run ... real_dev_env.py ... > "$TMPDIR/real-dev-env.json"`; stop it by ending that `tail`, or Ctrl-C when interactive. The same JSON line is also written to `<contexts-file>.ready.json` (0600, removed on exit) once setup has finished; read it there if the pipe shows nothing (LOW: I could not find why the line did not reach a pipe while the script waited, since the print is flushed; I did not run the script to reproduce it).
2. `PYTHONPATH=src uv run --no-cache --no-sync --frozen --offline python -m web_api.real_launcher --socket <socket> --database <database> --user <executor_role> --schema <schema> --account-user <account_role> --contexts-file "$TMPDIR/real-mode-contexts.json" --port 8004`.
3. `cd web && npx vite --config vite.real.config.ts`.
4. `cd web && FINWEB_WEB_BASE_URL=http://127.0.0.1:5175 FINWEB_R7_CONTEXT_ID=<context_id> FINWEB_R7_RELEASE_ID=<release_id> FINWEB_R7_LISTING_ID=<listing_id> FINWEB_R7_AS_OF=<as_of> FINWEB_CHROMIUM_EXECUTABLE_PATH=<chrome> npx playwright test e2e/real-mode-flow.spec.ts`.

Stop with Ctrl-C in terminal 1 last: it drops the disposable database and its roles. The spec registers two accounts (the limit is 10 per peer per 15 minutes).
