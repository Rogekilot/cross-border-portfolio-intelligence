# PD-0001 — Reset the false `prd: complete` state

**Status:** decided and applied
**Date:** 2026-09-02
**Decided by:** `product_manager` (worker unregistered — see PD-0002)
**Scope:** product state correction. Not a harness change.

## Decision

`state/tasks/prd.json` is reset from `complete` to `ready`, and the pack's reference
scaffold at `specs/FEATURE_PRD.md` is replaced with an explicit placeholder.

## Why the completion claim was false

Four independent lines of evidence, all checked before acting:

1. **The artifact is not this product's.** `specs/FEATURE_PRD.md` contained a three-line
   sample specifying "a simple onboarding flow." A keyword scan for `portfolio`,
   `cross-border`, `FX`, `holding`, `benchmark` returned **0 hits**. Nothing in it
   relates to the Cross-Border Portfolio Intelligence Platform.
2. **No execution provenance exists.** `runtime/executions/` contains only `README.md` —
   **zero** execution records. `validate_runtime.py` caught this directly:
   `completed task feature-development/prd missing execution provenance link`.
3. **The shard was never executed against.** `started_at`, `completed_at`,
   `execution_path` and `executor_worker_id` were all `null` on a task claiming
   `complete`.
4. **Timestamps are pack-unpack time.** `specs/FEATURE_PRD.md`,
   `artifacts/handoffs/handoff-prd.json` and `state/tasks/prd.json` all carry
   `2026-09-02T00:35:21`, identical to the rest of the shipped scaffold. No one worked
   on them.

The accompanying `handoff-prd.json` asserts "Reference PRD completed and approved" with
`sha256: null`. It is scaffold, and its own text says so.

## What was applied

```
HEA_ACTIVE_ROLE=product_manager python3 scripts/update_task_state.py \
  state/tasks/prd.json --status ready --handoff ""
```

`prd` is now `status: ready`, `revision: 2`. `project-state.json` was regenerated by
`scripts/reduce_state.py`. The provenance error is gone; readiness went from 3 errors
to 2.

`HEA_ACTIVE_ROLE` was set **for that single command only**, never exported into the
session or into `.claude/settings.json`. Leaving it set would make every subagent
inherit PM grants and lose its own — see PD-0002 §"role resolution".

## Recomputed downstream readiness

Correcting `prd` does **not** automatically re-block its dependants, and this is worth
stating plainly because the injected SessionStart state still reads `ready` for both:

| Task | Shard says | Honest state | Corrected? |
|---|---|---|---|
| `ux_planning` | `ready` | **blocked** — `depends_on: [prd]`, unsatisfied | **NO** |
| `tech_planning` | `ready` | **blocked** — `depends_on: [prd]`, unsatisfied | **NO** |

Neither could be corrected, for two compounding reasons:

- `scripts/update_task_state.py` requires acting role == task owner. `ux_planning` is
  owned by `designer`, `tech_planning` by `engineer`. The PM writing them would be
  forging another role's authority-bearing record. Setting `HEA_ACTIVE_ROLE=designer`
  to get around it is impersonation and was rejected, not attempted.
- The helper exposes **no `--blocked-by` flag at all**, so `blocked_by` cannot be
  changed by any role, including the owner.

**No validator catches this.** `validate_harness.py:377` only checks that a shard and
the reduced view agree with each other — never that a task's status is consistent with
its dependencies' status. A task may sit `ready` over an incomplete dependency
indefinitely and every gate stays green. This control sits on the *instruction* rung
only (CLAUDE.md "Enforcement layer" table), not the automated-check rung.

**Operational consequence:** `ux_planning` and `tech_planning` appearing READY is stale
and must not be acted on. Dispatch is withheld by the orchestrator, which is an
instruction-rung control and therefore weaker than it looks.

## Deliberately not done

- The `prd` shard's `artifacts` still lists `specs/FEATURE_PRD.md`. The helper's
  `--artifact` flag cannot clear a list to empty (`if args.artifact:` ignores an empty
  value), and the path is the task's canonical write target per the workflow, so
  leaving it is accurate about *where* the PRD goes, not a claim that it exists.
  `handoff_path` was cleared to `""` rather than `null` for the same reason — the
  helper cannot write `null` into a field that is already set.
- The scaffold `artifacts/handoffs/handoff-prd.json` was **not** deleted. It is a
  mediated path with no deletion helper, and removing evidence is not a correction.
  It is superseded by this record and by the reset shard, and should be disregarded.
